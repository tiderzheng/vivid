# 抖音摘要兜底命名设计

## 背景

抖音标题探测不稳定，现有流程在拿不到远端标题时会回退到媒体文件名或来源 ID。对抖音链接来说，这通常不是用户想要的项目命名。

## 目标

仅在抖音来源、未显式指定 `project_name`、且前置标题探测失败时，允许流程先继续执行；等 AI 总结生成后，再用 `summary.one_line` 作为最终项目名，并将工作目录同步重命名。

## 非目标

- 不修改 Bilibili、本地文件、其他平台的命名逻辑
- 不改变已拿到远端标题或用户手工指定标题时的行为
- 不把“摘要后命名”变成通用默认策略

## 方案

1. 保留现有前置标题探测。
2. 如果平台是抖音且前置标题缺失，先使用现有兜底标题把 staging 目录移动到临时最终目录，保证下载/总结链路不被阻塞。
3. 总结完成后，提取 `summary.one_line`，经现有 `sanitize_name()` 清洗后作为候选标题。
4. 若候选标题有效且与当前标题不同，则把工作目录再次重命名到新的最终目录，同时重定位 `transcript.media_path` / `audio_path`，更新 `source.title` 与 checkpoint。
5. 记录一个专门的诊断事件，说明命名来自摘要兜底。

## 风险控制

- 只在非 resume 且抖音兜底路径触发，避免影响断点续跑
- 仍然使用 `move_to_final_workdir()`，复用现有重名后缀策略
- 在写 artifacts 前完成重命名，避免产物路径与元数据不一致
