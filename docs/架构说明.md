# 架构说明（瞬知 / Vivid）

这份文档讲的是：

**瞬知**（Vivid） 现在是怎么组织的，数据和调用是怎么流动的。

## 1. 总体架构

**瞬知**（Vivid） 采用的是：

- 一个主程序
- 一个统一 skill
- 若干运行时 helper

对应关系：

- **瞬知**（Vivid） = 主程序
- `vivid-operator` = 统一 skill
- `tools/bilibili/` / `tools/douyin/` = 内嵌下载器（开箱即用）

## 2. 分层结构

当前可以把项目分成五层。

### 1. 入口层

负责接收用户或 agent 请求。

主要入口：

- `app.cli`
- `app.web`
- `scripts\vivid_tool.*`
- `skill\vivid-operator`

说明：

- `scripts\vivid_tool.*` 是仓库内主控制脚本
- `skill\vivid-operator` 提供的是 agent 侧 wrapper 入口，最终仍会转发到主控制脚本

### 2. 编排层

负责把整条速看流程串起来。

核心模块：

- `app\pipeline\orchestrator.py`
- `app\pipeline\acquisition.py`
- `app\pipeline\summarization.py`

这一层解决的是：

- 先做什么
- 后做什么
- 失败时怎么回退

### 3. 适配层

负责对接具体工具或外部能力。

当前主要包括：

- `app\adapters\bilibili.py`
- `app\adapters\douyin.py`
- `app\adapters\ytdlp.py`
- `app\adapters\ears4.py`
- `app\adapters\eyes.py`
- `app\adapters\llm.py`

### 4. 内部子系统层

负责项目内部已经收口的能力。

当前有三个关键子系统：

- `transcription`
- `vision`
- `summary`

它们分别对应：

- 内部转录
- 内部视频 OCR
- 内部摘要 prompt 配置与解析

### 5. 服务层

负责项目内部通用能力。

例如：

- 路径处理
- 命名
- 产物写入
- `ffmpeg` 查找
- 依赖引导

## 3. 主流程架构

从请求到产物，当前主流程如下。

### Step 1. 接收输入

输入可能来自：

- CLI
- Web UI
- skill 控制脚本

### Step 2. 平台识别

系统判断输入属于：

- `local`
- `bilibili`
- `douyin`
- `generic`

### Step 3. 获取字幕或媒体

按平台走不同分支：

- `local`
  - 直接使用本地文件
- `bilibili`
  - 先尝试字幕
  - 再下载媒体
  - 使用内嵌 helper `tools/bilibili/bili23_agent_cli.py`
- `douyin`
  - 下载媒体
  - 使用内嵌 helper `tools/douyin/douyin.js`
- `generic`
  - 使用 `yt_dlp`

### Step 4. 获取文本

默认主路径：

- 内部 `Whisper`

视频场景下也支持：

- 内部 OCR

支持三种策略：

- `auto`
- `prefer_ocr`
- `force_ocr`

### Step 5. 生成摘要

文本拿到后：

- 调用摘要模型
- 生成一句话总结
- 生成详细摘要
- 生成关键要点

### Step 6. 写出产物

最终保存：

- `quickread.md`
- `transcript.txt`
- `summary.md`
- `summary.json`
- `metadata.json`

## 4. 下载架构

这个点必须单独说明。

### Bilibili

当前不是走通用下载器，而是固定走内嵌 helper：

- `tools/bilibili/bili23_agent_cli.py`

原因：

- 需要字幕优先策略
- 需要更适合 Bilibili 的能力模型
- 这条链路来源于 `bili-downloader-agent`，但在当前项目里已经内嵌收口

### Douyin

当前固定走内嵌 helper：

- `tools/douyin/douyin.js`

原因：

- 这是当前项目明确指定的抖音下载链路
- 这条链路来源于 `douyin-download`，但在当前项目里已经内嵌收口

### Generic

其他通用站点才走：

- `yt_dlp`

## 5. 转录架构

当前转录架构分为主路径和回退路径。

### 主路径

- **瞬知**（Vivid） 内部 `Whisper`

相关模块：

- `app\subsystems\transcription\engine.py`
- `app\subsystems\transcription\whisper_service.py`

### 回退路径

- `Ears4`

只有在配置允许时才启用。

## 6. OCR 架构

当前 OCR 架构同样分为主路径和回退路径。

### 主路径

- `opencv` 抽帧
- OpenAI 兼容视觉 API 识别字幕

相关模块：

- `app\subsystems\vision\engine.py`

### 回退路径

- `Eyes`

只有在配置允许时才启用。

## 7. skill 架构

`vivid-operator` 的定位不是业务实现，而是统一控制面。

所以 skill 层负责：

- 给 agent 一个稳定入口
- 调用 `vivid_tool.*`
- 返回稳定 JSON

skill 不负责：

- 重写下载逻辑
- 重写转录逻辑
- 重写 OCR 逻辑

## 8. Web UI 架构

Web UI 是主程序的一部分，不是单独项目。

它负责：

- 提交任务
- 展示任务状态
- 展示历史记录
- 展示日志
- 下载产物

Web UI 背后仍然调用同一条编排链。

## 9. 当前架构结论

现在的架构核心可以概括为：

- **入口统一**
- **编排统一**
- **下载分流明确**
- **主路径优先内部执行**
- **回退路径保留兼容**

这也是当前项目对外应该坚持的说明方式。
